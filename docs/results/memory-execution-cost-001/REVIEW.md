# 同一存储合同下，减少重复准入检查即可降低执行成本

2026-10-08，eex005。固定已验收 `burst_256 + bounded`，保留全部内存 burst、
BookSim 调用和完整日志。s16/s64 的执行阶段墙钟中位数分别从 **1.781/6.407 s**
降至 **0.576/1.521 s**，即 **3.09×/4.21×**。应用时间、完整服务与生命周期、
消息事件以及原生命令/回复均完全一致。

这是同合同的实现优化，不是新模拟抽象或原生 WoW 标定。上一轮涉及内存请求
政策、消息误差与 RX 容量的结论全部保留；没有通过增大 burst 或改变仲裁换取速度。

## 先测成本，再选择修改层

先登记[成本检查及固定合同](../../MEMORY_EXECUTION_COST.md)，然后运行修改前的
两份完整 block。每份三次无 profiler 冷进程计时，另一次仅在 `execute` 内启用
cProfile。分析发现主要 Python 成本是反复调用任务准入及容量检查：内部 burst
或 packet progress 后，即使输入可用性、控制依赖和容量都没变化，仍扫描等待任务。

| 完整工作 | 修改前 admission 调用 | 修改后调用 | 应用 cycles，前后相同 |
|---|---:|---:|---:|
| s16 | 187,549 | 6,094 | 13,437 |
| s64 | 732,915 | 6,095 | 55,539 |

因此本轮没有合并内存服务事件。修改仅是在初始时刻、数据发布或任务退休之后
重新检查准入。退休即使不产生输出，也可能释放容量或满足控制依赖，仍触发扫描。
扫描内部保持原来的拓扑顺序、依赖首次满足时间和同周期执行顺序。

在当前合同中，只有这些状态变化能使未启动任务变得可执行：服务进度不直接
发布部分对象，DMA 占用也不改变已预留的对象容量。若未来加入部分对象消费、
外部存储释放或动态容量变化，必须相应增加准入失效通知，不能沿用此假设不检查。

| 完整工作 | 修改前执行墙钟，中位数 [范围] s | 修改后执行墙钟，中位数 [范围] s | 执行加速 |
|---|---:|---:|---:|
| s16 | 1.781 [1.777, 1.788] | 0.576 [0.571, 0.584] | 3.09× |

Python 执行阶段 CPU 时间中位数从 1.438/5.610 s 降为 0.240/0.734 s。
Python lifetime RSS 峰值分别为 86,556→86,152 KiB 和 94,664→94,584 KiB；
原生进程峰值仍约 9–10 MiB，不宣称显著降低内存使用。

执行时间不含图构建、初始化、结果序列化和独立审计；这些成本单独列在
[cost.csv](cost.csv)。原生子进程 CPU 是 lifetime 总量，没有将退出时的统计
误称为某阶段的精确原生 CPU 时间。两版依次运行，均固定 CPU 254/255，保留负载
记录；这是三次冷进程样本的观察值，不是交替随机化的大规模性能实验。
profiled 样本全部排除出计时比。Profiler 累计时间包含子调用和等待，不能相加
或解释为 BookSim 内部计算时间。

优化后网络包装及进程通信成为更大的成本部分；本轮到此停止，不继续改 native
步进、credit 或路由。空的应用消息表不保证网络内的信用已经排空。

## 模型决定

保留本轮精确执行优化，保留原来的详细内存请求与有限 RX 模型。较细合同此前
运行较慢，部分原因是可消除的重复检查；不能直接据此认定需要更粗的硬件合同。
这项改动降低了后续同机精度—成本研究的参考成本，但没有证明内存 burst 或
接收反馈可以省略，也不把它包装为新的通用模拟方法。
